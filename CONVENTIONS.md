# Conventions

Direct instructions for Claude (or any AI assistant) to follow when building web apps or
canvas/artifact deliverables for Adam. Read this in full before starting work. Follow it as
rules, not suggestions, unless Adam's own request in the moment explicitly overrides a rule here.

This draft was generated by scanning ~50 of Adam's existing repos for recurring patterns. Treat
it as a strong starting point, not gospel — edit anything that doesn't actually match what you
want going forward.

## Which Track Is This?

Before applying anything else below, decide which track applies. The two tracks diverge on
things that actually matter (privacy, accessibility, what "done" looks like) — if it's unclear
from the request, ask.

| Signal | Track |
|---|---|
| Built for a class, students will use it, submitted via Canvas LMS, used in a classroom | 🎓 **School / Teaching** |
| Personal tool, art piece, one-off experiment, toy, something just for Adam | 🎨 **Personal / Creative** |

### 🎓 School / Teaching Deliverables

- **Privacy is non-negotiable**: these repos are public by default — never commit student
  names, access codes, or keys.
- Keep activity/lesson folders at the **top level** of the repo, never nested — Canvas links and
  QR codes point directly at `/activity-name/`, and moving them breaks those links.
- End the flow with a **deliverable/receipt generator**: a "Generate summary" button that builds
  a plain-text completion receipt, a "Copy" button for the clipboard (so students can paste it
  into an LMS submission), and a "Start fresh" reset.
- If the app uses audio or the mic, add a footer disclaimer: *"Audio is synthesized in your
  browser — nothing is uploaded."*
- Take accessibility seriously — these run on classroom phones/tablets: `aria-label` on every
  canvas/visualizer, 44px+ touch targets, mobile-first layout.
- For interactive lessons, default to the **Lessons / Playground / Quiz / Challenge** tab
  structure (see Component Patterns) rather than inventing a new information architecture.
- License: MIT is fine — these are teaching tools/code, not standalone creative work.
- The actual requirement is that it deploys cleanly to GitHub Pages as a static site — not that
  it was *built* with zero tooling. Vanilla HTML/CSS/JS with no build step is usually the
  fastest way to get there, but a build step (Vite, Astro, etc.) is a legitimate choice when it
  genuinely helps (a full slide deck, a more complex app) — don't add one for its own sake, but
  don't avoid one on principle either.

### 🎨 Personal / Creative Projects

- Versioned iteration files (`spirographV1.html`, `V2.html`, ..., or a `gen2_claudeV1.html` per
  model tried) are worth keeping around breaking changes or big redesigns — not for every save,
  just the moments worth being able to come back to.
- Looser accessibility/mobile bar — polish for the actual audience, which is often just Adam.
- No Canvas-specific receipt/export needed, but consider `localStorage` to persist progress
  across sessions, and an export or email option if sharing/saving results matters for the piece.
- Same privacy sanity check as School projects, just scaled down: don't commit secrets, API
  keys, or other people's private info — it's still a public GitHub repo even if it's "just for
  me."
- License: MIT is a software license for reusable code — for art-forward pieces, a Creative
  Commons license (e.g. CC BY-NC-ND) usually fits the intent better. Ask which the piece calls
  for rather than defaulting to MIT here.
- More palette freedom — dark-academia (gold accent + serif), stark minimal (pure black/white),
  or whatever fits the piece's mood. The palette families below are starting points, not limits.

## General Principles

- The actual requirement is a clean deploy to GitHub Pages as a static site — not "zero build
  tooling" as an end in itself. Default to vanilla HTML/CSS/JS with no build step, since that's
  usually the simplest way to get there, but a build step (Vite, Astro, Next.js) is a legitimate
  choice once a project genuinely needs routing, TypeScript, or a component library. Don't reach
  for a framework preemptively, and don't avoid one out of principle either — pick whichever
  gets to a working GitHub Pages site with the least fuss.
- Ship a fully self-contained deliverable: one HTML file with inline `<style>`/`<script>`, or a
  small hand-written set of `css/` and `js/` files loaded via plain `<script>`/`<link>` tags,
  unless it's graduated to a real build per above.
- Every interactive tool needs a working reset/restart control.
- Prefer real browser APIs over wrapper libraries — e.g. the native Web Audio API directly,
  rather than Tone.js, unless the app also needs music notation rendering (see Libraries to
  Prefer).

## File / Project Structure

- Single-file default: `index.html` with inline `<style>` and `<script>` for anything simple
  enough to fit.
- Once a project grows past what fits comfortably in one file, split into `css/style.css` +
  `js/` with one file per concern (e.g. `audio-engine.js`, `ui.js`, `state.js`,
  `visualizer.js`).
- Use ES modules (`type="module"`, `import`/`export`) once split across multiple JS files; plain
  `<script>` tags are fine for true single-file apps.
- Ship a `LICENSE` — MIT by default for code-forward/School projects; see the licensing note in
  the Personal/Creative track above for when Creative Commons fits better instead.
- Add a `.github/workflows/static.yml` GitHub Pages deploy workflow (checkout → configure-pages
  → upload-pages-artifact → deploy-pages) so the repo deploys itself.
- Add a `.claude/launch.json` for local dev, defaulting to `python3 -m http.server <port>` — no
  JS dev server needed for a static app.
- Keep READMEs terse: what the thing is, how to run it locally, and a link to the live GitHub
  Pages URL. Save longer docs for genuinely complex apps.
- If retiring/moving a project, leave a redirect stub (`<meta http-equiv="refresh">` +
  `location.replace()`) pointing at the new URL rather than deleting the repo.

## Styling Conventions

### Colors

- Always define the palette as CSS custom properties on `:root` — never hardcode hex values
  inline in rules.
- Default to dark-mode-first. Use `@media (prefers-color-scheme: dark)` (or `light`) for the
  override rather than shipping a manual light/dark toggle button, unless the app specifically
  calls for one.
- These two palette families are recurring patterns already in use, not a mandatory pick-one —
  plenty of the reference repos deviate. Reach for one when it fits, not by default:
  - **Dark lab/tool palette**: near-black navy background (`#0a0a10`–`#101825` range), a single
    bright cyan/teal accent (`#5dd2ff`, `#66d9ff`, `#7ce0ff`, `#45e8c0`), a warm secondary accent
    (`#ff8a3d`, `#ffab4e`). The most common default when nothing else is specified.
  - **Warm editorial/hub palette**: cream/paper background (`#f6f1e9`–`#f7f2ea`), dark ink text
    (`#192431`/`#19221e`), teal or forest-green accent (`#0f766e`, `#14503d`), warm orange
    secondary (`#c66a1d`). Good for landing/hub pages and long-form lesson content — not a
    requirement for those either, just what's shown up most.
- Always define semantic status colors: `--success`/`--ok` (green), `--warning`/`--warn`
  (amber), `--danger`/`--error` (red) — keep names consistent within a project.
- For hover/glow states, pair a solid accent with an alpha or `-dim`/`-glow` variant (e.g.
  `--accent-glow: rgba(...)`) instead of hand-picking a second unrelated hex value.
- Use `color-mix(in oklab, var(--accent) NN%, transparent)` for tints/borders when you need a
  derived shade.

### Typography

- Pick one of two pairings depending on tone:
  - **Tool/utility apps**: system font stack only — `-apple-system, BlinkMacSystemFont, "Segoe
    UI", Roboto, sans-serif`. No web fonts.
  - **Editorial/teaching apps**: a serif display face (Fraunces, Cormorant Garamond, or Cinzel)
    for headings + a grotesque sans (Space Grotesk, Inter, Manrope, or DM Sans) for body text,
    optionally plus a monospace face (JetBrains Mono, IBM Plex Mono, DM Mono) reserved for
    numeric readouts/labels.
- Load Google Fonts with the standard double-preconnect pattern:
  ```html
  <link rel="preconnect" href="https://fonts.googleapis.com">
  <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
  <link href="https://fonts.googleapis.com/css2?family=...&display=swap" rel="stylesheet">
  ```
- Reserve monospace/tabular-nums for numeric/technical readouts (dB values, timers, counters),
  not body text.

### Spacing

- Use a consistent border-radius scale as CSS variables (`--radius-sm/md/lg`, roughly 8–16px for
  cards, up to ~27px for larger panels) and `999px` for pill-shaped buttons/badges. Avoid sharp
  corners entirely.
- Default to a mobile-first single-column layout, centered, with a max-width in the 460–1100px
  range; add columns only via `@media (min-width: ...)` breakpoints, never as the base layout.
- Add safe-area padding (`env(safe-area-inset-*)`) and `touch-action: manipulation` for anything
  meant to be used on a phone/tablet.

## Component Patterns

- **Hero header**: a small-caps "eyebrow" label above an `<h1>`, a one-sentence subtitle below
  it, optionally a row of pill-shaped status chips ("Audio Idle", "Mobile Friendly").
- **Screen-swap SPA shell**: a single `#app` root containing `.screen` sections toggled via an
  `active` class (welcome → loading → main → results) for multi-step flows — no router needed.
- **Tabbed learning module**: Lessons / Playground / Quiz / Challenge tabs sharing one page —
  the default IA for School/Teaching interactive lessons (see Which Track above).
- **Audio-unlock gate**: any app using Web Audio must show a full-screen "Enable/Start Sound"
  overlay before creating/resuming an `AudioContext`, to satisfy the browser's autoplay policy
  (call out iOS silent-mode behavior if relevant). Applies to both tracks.
- **Sticky topbar**: `position: sticky` header with `backdrop-filter: blur(8–12px)` over a
  translucent background.
- Always include a working reset/restart affordance somewhere in an interactive tool.

## Naming Conventions

- JS: camelCase for variables, functions, and element ids.
- CSS: kebab-case for class names and multi-word ids.
- Files/modules: kebab-case (`audio-engine.js`, `time-tracker.js`).
- Cache DOM lookups once: a `$ = id => document.getElementById(id)` shorthand plus a single
  `elements` object built at startup, rather than repeated `getElementById` calls scattered
  through the code.
- Keep one central `state` (or `store`) object literal holding app state; for anything with
  distinct phases, consider a small explicit state machine (a `States` map + a `transition()`
  guard) over ad hoc boolean flags.
- Surface an `APP_VERSION` constant in the UI (footer or settings), using either semver
  (`v1.2.0`) or a date-based scheme (`vYYYY.MM.DDx`).
- Config-as-data: put tunable parameters in one config object (e.g. a `KNOBS` map of `{min, max,
  default, unit, fmt}`) rather than scattering magic numbers through event handlers.

## Canvas / Artifact Defaults

### Layout

- Default to a full-bleed or hero-sized `<canvas>` for the primary visualization, or a small
  dedicated canvas per meter/scope when there are several (spectrum, waveform, goniometer,
  etc.) — don't cram unrelated visualizations into one canvas.
- Size the backing buffer with `devicePixelRatio` (`canvas.width = canvas.offsetWidth * dpr`)
  and resize on `window.addEventListener('resize', ...)`.

### Interactivity

- Drive animation with `requestAnimationFrame`. If a page has multiple animated canvases,
  prefer one shared rAF dispatcher (a `subscribe(fn)`/unsubscribe pub-sub ticked from a single
  loop) over spinning up one `requestAnimationFrame` loop per visualization.
- Add `aria-label` to canvases used as visualizers, since their content isn't otherwise
  accessible as text.

### Libraries to Prefer

- Native Web Audio API directly (`AudioContext`, `createGain`, `BiquadFilterNode`,
  `DynamicsCompressorNode`, `AnalyserNode`, `OfflineAudioContext`) for audio DSP — don't reach
  for Tone.js by default.
- **Tone.js** only when also rendering music notation (paired with VexFlow or abcjs) — that
  combination shows up specifically for notation+playback, not general audio work.
- **VexFlow** or **abcjs** for music notation rendering.
- **Three.js** for genuine 3D visualizations.
- **SortableJS** for drag-and-reorder interactions; **marked** for rendering Markdown content
  client-side.
- ES modules for anything split across multiple JS files; plain `<script>` for genuine
  single-file apps.

### Libraries to Avoid

- No React, Vue, or other component frameworks for a single-purpose artifact — graduate to a
  real build (Vite/Next/Astro) only if the project genuinely can't be a static page anymore, and
  treat that as an exception.
- No Tailwind or other utility-CSS frameworks — hand-write CSS with `:root` custom properties
  instead.
- No jQuery, Chart.js, or p5.js — none of these have shown up in any reference repo; stick to
  native Canvas/WebGL/Web Audio APIs.
